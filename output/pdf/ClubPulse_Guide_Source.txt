ClubPulse website guide

Product walkthrough and launch instructions

Prepared for the club project team and hackathon presenter<br/>24 October 2026

ClubPulse lets participants submit event feedback with a one-use code, then gives authorised organisers a protected event report and tools to plan improvements. This guide explains the current website, how its privacy design works, how to run it, and the steps required before a public club launch.

<b>Current status:</b> the local preview and production build are available. No GitHub push, public deployment or custom-domain connection has been completed. The application still needs production infrastructure verification. This document distinguishes implemented features from future work.

Read this first

The website has two entry points. Participants use event codes and never receive administrator privileges. Administrators use email and password to manage events, issue invitations, and read released reports. Participant sign-in verifies event eligibility without creating a named account.

Design and demo data

The interface uses paper tones, black typography, yellow highlights, red accents and square controls. It includes a favicon and locally hosted fonts, with no AI badge or third-party trackers. The preview has one 24-Hour Hackathon and five explicitly synthetic ratings: 5, 4, 4, 3 and 5. Their frozen average is 4.2 out of 5. New test submissions do not change that fixture.

The security boundary

A hidden button is not an access control. Each administrator API checks a valid server session with the admin role. Opening an administrator URL without signing in displays the sign-in form. Participant codes, signed participant tokens and fabricated session cookies do not grant administrative access.

The app has one configured administrator credential pair, not a multi-user organisation directory. There is no self-service admin registration, password reset, administrator invitation system or MFA in the current implementation. Manage credentials through the deployment environment.

Shared computer rule

Sign out of the administrator workspace before giving the device to a participant, or use separate browser profiles. A browser already signed in as administrator retains that access. Participant forms omit account cookies when sending invitations and feedback; that protects the submission flow, not a shared unlocked browser.

Public metadata

Visitors can see event names, descriptions, dates and open status. Public event endpoints do not return feedback, reports, private signing keys or response counts.

Participant and administrator workflows

Participant journey

<b>1.</b> Obtain the event link and one unique invitation code from the organiser. Codes are distributed manually; the app does not send email or SMS.

<b>2.</b> Open Participant sign-in, select the event and enter the code. In local preview, Use demo code only fills the field. Nothing is transmitted until Sign in with event code is pressed.

<b>3.</b> The browser creates a random token and blinds it. The issuer receives the invitation code and blinded token, validates the code and signs the blinded value. The browser unblinds the signature.

<b>4.</b> Choose a rating from 1 to 5, select Content, Delivery, Organisation or Other, and optionally write up to 2,000 characters. Remove names, team names and identifying details.

<b>5.</b> Submit. The collector receives the event, rating, topic, comment and signed token. It does not receive the invitation code, account cookies or referrer. Each valid token can be accepted once.

The browser keeps an unfinished token exchange in session storage for retry. Losing that storage may lose access to an already exchanged invitation. There is no email recovery because no participant email is collected. There is currently no participant reply inbox or receipt lookup.

Administrator journey

<b>1.</b> Sign in, open Events, and create the event with a name, date and description. New events accept feedback immediately.

<b>2.</b> Open Manage invitations. Generate 1 to 200 codes per request and download them immediately. Share one code per attendee. Plaintext codes are not retrievable later from the database.

<b>3.</b> Copy the event-specific participant link. Keep the administrator password and the full invitation list private. Avoid keeping an identity-to-code mapping if your club does not need one.

<b>4.</b> Close the event when collection finishes. Real reports require at least five responses and a full 15-minute cooldown after closure. Exact collection counts remain hidden.

<b>5.</b> Refresh Statistics after eligibility. The first eligible report request seals the report. A real event with a sealed report cannot reopen. Create a new event for a new cohort.

<b>6.</b> Review released comments, choose an organiser action, assign a responsible role and due date, and export the aggregate brief. Sign out when finished.

Statistics and organiser tools

Read the report

The report scope selects all sealed reports or one event. The overall score is a response-weighted average rounded to one decimal. The displayed response total is not attendance, a participation rate or a count of unique people. Someone receiving several valid codes could submit several responses.

Positive means rating 4 or 5. The positive percentage is released only if both the positive and non-positive groups contain at least five responses. With the five demo ratings, this metric stays protected. The 5+ voices label indicates the release minimum, not a positive percentage.

Explore without exposing participants

Rating bars support Count and Percent modes. The entire rating or topic breakdown remains withheld if any bucket or its complement has fewer than five responses. Changing units never bypasses suppression. Expand What these numbers mean for definitions. The release ledger shows collection, cooldown and report status.

Compare events accepts two real sealed reports and shows their rounded mean difference and cohort sizes. Demo reports are excluded. The comparison is descriptive; it does not establish statistical significance, participant-level change or causation. With only one synthetic event, the comparison explains how to unlock it rather than inventing a baseline.

Turn comments into work

Listening notes use simple keyword rules on released comments to suggest practical improvements. Review the source comments before acting. They are not AI sentiment analysis or measured prevalence. The released-comment search only searches text already present in the administrator browser.

The action board supports custom actions, responsible organiser roles, due dates, Planned / In progress / Done status, a completion bar, suggestions from listening notes, removal with undo, and JSON download. Each report scope has its own board. A separate free-text action-plan note is also retained.

<b>Storage limit:</b> action boards and notes are saved only in the current browser. They are not shared between administrators and can be lost when browser data is cleared. Download private action files when needed. Do not add participant identities.

Anonymity and data architecture

Two services with different responsibilities

React runs in the browser. The Express collector serves the website, handles administrator sessions and verifies anonymous feedback. A separate issuer owns invitation hashes and private event signing keys. MongoDB persists the two services in separately scoped databases. Local demo listeners share this computer and process; production needs separate HTTPS origins and service processes.

Browser → issuer: invitation code + blinded token.<br/>Issuer → browser: blind signature.<br/>Browser → collector: feedback + unblinded token + signature.<br/>Administrator → collector: authenticated event management and sealed reports.

The implementation uses Cloudflare blindrsa-ts and the RFC 9474 RSABSSA-SHA384-PSS-Randomized suite, with a 2048-bit RSA key per event. The collector holds only public keys. Canonical token hashes and database uniqueness reject replay attempts, including alternative Base64 formatting.

Location | Stored information

Issuer database | Event private/public keys; invitation hashes; blinded-request hashes used for exchange retry protection.

Collector database | Event metadata and public keys; random feedback UUID, event ID, rating, topic, comment and unique token hash; sealed reports.

Server memory | Administrator sessions and temporary rate-limit keys derived from network addresses.

Participant browser | Pending exchange and signed token in session storage until completion.

Administrator browser | Action notes and board tasks in local storage.

What is deliberately absent

Feedback records contain no name, email, invitation code, IP address, user-agent or submission timestamp. Released comments are shuffled and detached from rating, topic, row ID and time. Reporting APIs permit whole-event scope only. Reports are fixed after release to reduce differencing attacks.

What anonymity does not guarantee

Hosting providers can observe network addresses and timing. Operators with broad infrastructure access may correlate traffic. Database access can expose raw feedback. Identifying comments can reveal their author. Threshold rules are not differential privacy and do not stop all inference. The complete application has not had an independent security audit.

Local setup and troubleshooting

Start the temporary preview

Install Node 24, open PowerShell in the project directory, and run the following commands. The current working preview may already be running; do not start another process on the same port.

cd C:\Users\2026\Documents\ChatGPT\clubpulse<br/>npm ci<br/>npm run dev

Open http://localhost:3000. The collector listens on port 3000 and the demo issuer on 3001. Without a database URI, local development uses temporary memory. Restarting clears events and submissions, recreates the fixture and invalidates administrator sessions.

Local preview item | Value

Administrator email | admin@clubpulse.local

Administrator password | local-preview-only

Participant demo code | HACKATHON-DEMO-2026

These are local demonstration credentials only. Production forbids demo mode. The demo code works once per restart; generate fresh invitations to test more participants.

Use persistent databases

<b>1.</b> Create collector and issuer databases with separate users. Collector transactions require a MongoDB replica set, such as an appropriately configured Atlas cluster. A standalone MongoDB server is insufficient.

<b>2.</b> Copy .env.example to .env and .env.issuer.example to .env.issuer. Fill in the database URIs and secrets. Keep the files private and out of Git.

Copy-Item .env.example .env<br/>Copy-Item .env.issuer.example .env.issuer<br/>node --env-file=.env.issuer server/issuer.js

<b>3.</b> Leave the issuer terminal running. In a second terminal, run npm run dev. With persistent configuration, create real test events; the synthetic fixture is disabled.

Common problems

<b>Code already exchanged:</b> resume in the same tab if its token remains. Otherwise ask the organiser for a replacement. <b>Protected report:</b> check event closure and the full cooldown; fewer than five responses stay private. <b>Login lost after restart:</b> expected because sessions are in memory. <b>Port already in use:</b> stop the existing project process or choose consistent collector and issuer ports. <b>Issuer request fails:</b> check its service health, origin configuration and shared secret.

Production configuration

Deploy two Node web services and persistent MongoDB databases. Static-only hosting cannot run the backend. Choose hosting and a domain you control, review the provider billing screen, and configure the following values. No purchase has been made by this project.

ADMIN_EMAIL / ADMIN_PASSWORD | Your private administrator credentials; password at least 12 characters.

SESSION_SECRET | Independent random secret, at least 32 characters.

ISSUER_ADMIN_SECRET | Random shared service secret, at least 32 characters.

ISSUER_URL | Different HTTPS issuer origin, no trailing slash.

Issuer environment | Required value

NODE_ENV / DEMO_MODE | production / false

Build and start commands

Collector: build with npm ci followed by npm run build; start with npm start. Health endpoint: /api/health. Issuer: build with npm ci; start with npm run issuer. Health endpoint: /health. Let the host supply PORT for each service.

Generate secrets locally

node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"

Run this separately for each independent secret. Never copy real values into screenshots, this document, source code or a public issue. Match only the service-to-service secret across the two services.

Infrastructure requirements

Use one collector instance until shared session storage is added. Restrict database users and network access. Configure host, proxy and APM logging to avoid sensitive payloads. Test both HTTPS origins, CORS, TLS and persistence on the actual host. Separate origins alone do not prevent a common operator from correlating traffic.

Testing and operation

Run the project checks

npm test<br/>npm run build

The existing seven-test suite covers separate issuance, credential-free collection, admin route protection, forged signatures, replay, forbidden identity fields, cooldown, immutable reports, small-cell suppression, detached comments and aggregate-only export. It uses isolated temporary services and an accelerated test-only cooldown. Production keeps the full 15-minute wait.

Acceptance checks on your deployment

<b>1.</b> Without signing in, request statistics, exports, event creation, event updates and invitation generation. Each must require administrator authentication. A participant token must not grant admin access.

<b>2.</b> Create an event and generate five different invitations. Submit five legitimate test responses. Confirm the collector rejects an invalid signature and a replay of a used token.

<b>3.</b> While open, confirm exact response counts and comments stay hidden. Close the event, wait 15 minutes, then refresh. Confirm the eligible report releases and suppressed breakdowns stay hidden.

<b>4.</b> Restart the services. Verify the event report persists, comments keep their sealed order, used tokens stay spent, and a sealed real event cannot reopen. Administrator sign-in will be required again.

<b>5.</b> Add an action, move its status, reload, remove and undo. Confirm actions remain private to that browser. Download the brief and CSV; confirm no comments, codes or tokens appear. Review action JSON separately as private working material.

<b>6.</b> For event comparison, complete two real sealed events. Confirm the choices exclude synthetic demos and the displayed change matches the difference between rounded averages. Do not add fake events just to fill this view.

Operational responsibilities

Keep issuer keys available for existing events and restrict backup access. Define a club retention policy before real use; automatic scheduled deletion is not implemented. Back up both databases separately and practise restoring them. Keep Node and dependencies maintained. If a secret is exposed, rotate it through the hosting environment and review access logs using the minimum necessary metadata.

Answer likely judge questions

<b>Why no participant password?</b> The code proves event access without creating an identity record. <b>Can organisers trace feedback?</b> The protocol separates codes from tokens, but traffic metadata and identifying comments remain risks. <b>Why are some charts locked?</b> Small-group disclosure is intentionally limited. <b>Is this AI analysis?</b> No; current listening prompts use explicit keyword rules. <b>Does it scale across clubs?</b> The current configuration is one club with one admin credential pair; multi-tenant roles are future work.

Prioritised next work

<b>Before club launch:</b> complete live database and domain validation, mobile testing, backup restore and a retention policy. <b>Next product release:</b> shared action storage with role-based admin accounts, MFA and account recovery. <b>Later research:</b> privacy-preserving reply receipts, accessibility audit and an independent review of the end-to-end anonymity design. These items are not implemented features.

A strong presentation demonstrates one complete problem-solving journey and explains the trade-offs accurately. The code can support that demonstration; no feature list guarantees a competition result.
